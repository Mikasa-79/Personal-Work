**质量评估说明**：

- **类图设计（质量 4，修改 20%）**：AI 准确地将 P2 的模块边界映射为 Controller-Service-Mapper 分层结构，领域实体的属性和方法定义合理。主要修改集中在服务职责边界：`RequestService` 中混入了管理员审核方法，`OrderService` 中直接引用了 `RequestMapper`。人工审查后调整了这两个跨模块依赖。
- **API 规范（质量 4，修改 15%）**：AI 生成的 REST 接口路径、HTTP 方法、请求/响应结构规范统一。成功/失败响应格式和错误码体系设计完整。修改集中在补充权限边界说明（如"未登录用户只能浏览已审核通过的需求"）和增加 `CONFLICT`、`BUSINESS_ERROR` 等业务异常码的触发条件。
- **数据库设计（质量 4，修改 10%）**：AI 生成的建表 SQL 可直接执行，外键、CHECK 约束、唯一索引设计合理。`idx_help_requests_browse` 复合索引对公开列表查询的覆盖较好。修改很少，主要是确认隐私字段处理策略（`contact` 字段的展示范围）和补充 `ck_orders_different_users` 约束。
- **设计文档整合（质量 4，修改 20%）**：AI 将类图、API、数据库、设计模式统一整合为详细设计文档，结构清晰。人工补充了需求追踪表（将设计元素映射到 FR-1 ~ FR-26）和安全设计章节的 XSS/参数化查询说明。
- **SOLID 检查准备（质量 3，修改 60%）**：AI 给出了检查框架和 6 个重点审查方向，但没有给出具体的违规判断。团队需要逐条分析类图中的依赖关系和服务职责，最终由人工完成全部 5 条原则的审查结论和修正方案。

## 2. AI 助力分析（Q1）

本阶段 AI 在以下方面提供了实质性帮助：

**（1）从架构到设计的快速落地**
AI 帮助把 P2 的"前后端分离 + 分层单体"架构决策落到具体类图、API 路径和数据库表结构。例如，P2 中定义的"认证模块"、"需求模块"、"订单模块"、"评价模块"、"通知模块"在 AI 生成的类图中被自然地映射为 Controller-Service-Mapper 三元组，减少了团队在命名和分层上的讨论时间。

**（2）核心对象字段和状态枚举的统一**
AI 帮助统一了 `User`、`HelpRequest`、`Order`、`Review`、`Notification` 等 7 个核心实体的字段定义和 8 组枚举值（`UserRole`、`UserStatus`、`RequestCategory`、`RequestStatus`、`AuditStatus`、`OrderStatus`、`OrderAction`、`NotificationType`）。这些枚举在类图、API 文档、建表 SQL 的 CHECK 约束中保持一致，避免了人工分别编写时容易出现的命名不一致、遗漏枚举值等问题。

**（3）REST API 的规范化输出**
AI 生成了统一的成功/失败响应结构、7 个标准错误码（`VALIDATION_ERROR` ~ `INTERNAL_ERROR`）以及每个接口的具体错误场景。这种规范化减少了前端对接时因响应格式不一致导致的返工。

**（4）数据库约束和索引的完整性**
AI 生成的建表 SQL 覆盖了外键约束、CHECK 约束、唯一索引和复合索引，特别是 `idx_help_requests_browse(audit_status, status, category, created_at)` 复合索引直接服务于需求列表的核心查询场景，说明 AI 具备从业务查询模式反推索引设计的能力。

**（5）设计模式识别和论证**
AI 识别出状态模式（`OrderStateMachine`）、策略模式（`CreditPolicy`）和模板方法（统一分页）三个设计模式应用点，并对"为什么用"和"不用会怎样"给出了可用的论证草稿。

**AI 没有替代团队完成的关键工作**：
- 最终的 SOLID 违规数量判断和修正方案由人工审查得出。
- 需求追踪表（FR-1 ~ FR-26 到设计元素的映射）由人工补充。
- 安全设计章节中 XSS 防护、参数化查询、BCrypt 策略等具体措施由人工审核确认。

## 3. AI 误导分析（Q2）

SOLID 检查中发现的 AI 设计问题数量：**3 处**

最严重的设计问题是：**`RequestService` 同时包含面向普通用户的 `publish`/`query`/`getDetail` 方法和面向管理员的 `audit` 方法，违反了单一职责原则**。这导致当管理员审核逻辑变更（如增加多级审核、审核理由模板）时，会影响用户端的发布/查询代码路径，增加不必要的回归风险。此外，`OrderService` 直接依赖 `RequestMapper` 而非通过 `RequestService` 修改需求状态，绕过了可能的业务校验，属于依赖倒转违规。

其他发现的设计问题：

**（1）NotificationService 对扩展未封闭**
`NotificationService` 按事件类型写了 `sendOrderChanged(Order)` 和 `sendReviewCreated(Review)` 两个具体方法。如果要新增"订单取消通知"类型，需要同时修改：① Java 枚举 `NotificationType`；② 数据库 CHECK 约束；③ `NotificationService` 类新增 `sendOrderCancelled()` 方法。三处同步修改容易遗漏，且修改 `NotificationService` 本身违反了开闭原则。修正方案：引入 `NotificationEvent` 接口，`NotificationService` 改为 `send(NotificationEvent event)` 统一分发，新增事件类型只需新增事件类。

**（2）OrderService 直接依赖 RequestMapper**
类图显示 `OrderService --> RequestMapper`，这意味着 `OrderService` 在接单时直接操作 `RequestMapper` 将需求状态改为 `LOCKED`。这绕过了 `RequestService` 中可能存在的业务校验（如检查需求审核状态、发布者是否被禁用等），属于跨模块的低层依赖。修正方案：`OrderService` 改为调用 `RequestService.lockRequest(id)`。

**（3）Controller 和 Service 之间缺少接口抽象**
所有 Controller 直接依赖具体 Service 类而非接口，虽然当前不影响功能运行，但降低了单元测试的可 mock 性和 Service 实现的可替换性。好的一面是，现有 Service 拆分粒度合理（每个模块一个 Service），引入接口的改动范围可控。

**AI 设计中没有出现的问题**（值得肯定）：
- 没有出现"一个 Controller 直接调用 Mapper"的情况，分层意识清晰。
- 没有出现"一个巨大的 CampusHubService 包含所有业务方法"的胖接口问题，接口隔离原则遵守良好。
- 前端 API 层（`AuthApi`、`RequestApi` 等）与页面组件（`LoginView`、`RequestListView` 等）分离，遵循了前端的分层实践。

## 4. Prompt 改进计划（Q3）

上阶段改进措施的验证结果：

- **P2 改进措施**：在 Prompt 中增加"项目周期、团队熟悉技术、核心功能、交付目标"等约束。
- **P3 验证结果**：本阶段在设计生成时沿用了详细约束输入策略（向 AI 提供 P1 需求 + P2 架构 + P3 任务说明），AI 生成的类图、API 和数据库设计与项目约束匹配度较高。例如 AI 自然选择了"分层单体"的分层结构而非微服务，API 路径保持在 `/api/` 下的一级资源命名。说明"提供完整上下文"的 Prompt 策略在 P2 和 P3 持续有效。

本阶段新的改进措施：

- **分离生成与审查**：在生成类图后，单独追加一次 SOLID 审查 prompt（"请审查以下类图中的 SOLID 违规"），而不是让同一次输出同时承担"生成设计"和"自查问题"两个角色。本阶段实践中发现 AI 做 SOLID 检查准备时只给出了问题方向而没有具体违规判断，可能正是因为"自我审查"的能力弱于"独立审查"。
- **要求可追踪输出**：在生成 API 时要求 AI 同时输出"每个接口对应的需求编号"（如 FR-5、FR-8），从源头建立设计到需求的追踪链，而不是事后由人工补填追踪表。
- **要求输出边界条件和错误场景**：在生成 API 文档时，明确要求 AI 对每个接口列出"至少 3 种可能的错误响应及其触发条件"。本阶段 AI 已覆盖了基本的错误码，但部分接口的错误场景不够完整（如完成订单接口未说明"非参与方尝试完成"的 `FORBIDDEN` 场景）。
- **四维快速校对法**：继承 P2 的"可行性 / 可维护性 / 可扩展性 / 风险"四维评估框架，在 AI 生成设计文档后团队按这四个维度快速打分，避免被单一维度的"看起来完整"误导。

## 5. 本阶段的核心工程判断

决策内容：

**将订单状态流转和信用分计算从 Service 中分离为独立的"规则对象"（`OrderStateMachine` 和 `CreditPolicy`），而不是将状态判断和评分逻辑直接写在 `OrderService` 和 `ReviewService` 的内部方法中。**

具体而言：
- `OrderStateMachine` 集中管理订单的合法状态转换表和操作者身份校验，被 `OrderService` 的每个操作方法（accept/confirm/start/complete）调用。
- `CreditPolicy` 独立计算评价后的信用分变化值，不嵌入 `ReviewService.create()` 的主流程。

为什么 AI 无法做这个决策：

**（1）AI 缺少对"课程评分标准"的认知**
AI 可以识别出状态模式和策略模式是可选的设计方案，但它不知道本课程项目对"设计模式应用"有明确的评分权重。团队需要在"AI 建议的多种模式"中挑选对验收最有利的模式，并决定模式的实现深度——例如 `CreditPolicy` 是做成单一计算类还是完整的策略接口+多实现，这个深度决策影响工时分配，AI 无法根据评分标准优化。

**（2）AI 无法衡量团队的测试能力和回归风险**
将状态逻辑散落在 Service 方法中（AI 可能认为这样"更简单"），对 AI 来说只是两种等效实现风格的差异。但团队知道自己只有 4 人且测试时间有限——如果状态判断分散在 5 个方法中，后续新增"取消"和"申诉"状态时需要修改每个方法并重新测试所有流转路径。`OrderStateMachine` 将状态规则集中后，测试只需要覆盖状态机本身的转换表。这个"用设计复杂度换测试可控性"的权衡，需要团队对自身测试能力和 bug 率的真实判断，AI 无法做出。

**（3）AI 偏好"当前够用"，而团队要考虑"迭代必然发生"**
AI 倾向于根据当前需求生成刚好够用的设计（如直接在 `OrderService` 方法中写状态判断），但团队从 P1/P2 经验中已经知道课程项目会经历多轮迭代（P0 → P1 → P2），需求扩展是确定性的。选择状态模式和策略模式是团队基于"订单状态必然扩展"和"信用规则必然调整"这两个工程预判做出的预防性设计决策，而非 AI 能自动权衡的。
