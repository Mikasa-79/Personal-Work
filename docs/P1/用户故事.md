# 人工编写

# 用例图

## 角色
- **管理员**：负责管理系统用户、查看系统日志、管理帖子信息等。
- **用户**：可以使用学号创建账号，发布帖子和评论，进行在线交流。
- **系统**：提供账号创建、帖子发布和审核，以及帖子按标签分区，根据关键词检索等功能。

## 用例
1. **用户登录**：用户可以通过输入学号和密码登录到系统。
2. **查看帖子**：用户可以查看平台上的帖子，查看帖子的标题、内容、图片、标签等信息。
3. **发布帖子**：用户可以发布带有标题、内容和标签的帖子，分享信息。
4. **发布评论**：用户可以在帖子下发布评论，评论内容对所有用户可见。
5. **在线交流**：用户可以与其他用户通过平台进行即时在线聊天，发送文本和图片。
6. **创建账号**：用户可以通过提供学号和基本信息注册账号。
7. **编辑帖子**：用户可以修改自己发布的帖子内容或删除已发布的帖子。
8. **查看个人资料**：用户可以查看和编辑自己的个人信息，包括头像、昵称、联系方式等。
9. **举报帖子**：用户可以举报不良内容或违规的帖子，管理员进行处理。
10. **管理员登录**：管理员可以通过用户名和密码登录到后台管理系统。
11. **管理用户**：管理员可以查看、编辑、删除用户信息，管理用户的权限。
12. **管理帖子**：管理员可以审核、删除、修改用户发布的帖子，保证内容符合平台规范。
13. **发送系统通知**：系统可以自动向用户发送通知，提醒评论、私信或帖子状态更新。
14. **查看系统日志**：管理员可以查看系统的操作日志，追踪平台活动和维护记录。
15. **系统退出**：所有角色可以退出系统，结束当前会话。

# 用例描述

## 用例 1: 用户登录

### 用例描述
- **用例名称**：用户登录
- **角色**：用户
- **目标**：用户能够通过学号和密码登录平台，访问其个人信息和相关功能。

### 前置条件
- 用户已经在系统中注册并拥有有效的学号和密码。
- 用户的学号和密码是正确且尚未过期。
- 用户处于平台的登录页面。

### 基本流
1. 用户访问平台登录页面。
2. 用户输入自己的学号和密码。
3. 用户点击“登录”按钮。
4. 系统验证用户的学号和密码。
5. 如果学号和密码正确，系统登录用户并显示主页或用户的个人信息。
6. 用户可以进行其他操作，如查看帖子、发布评论等。

### 替代流
- **替代流 1**：用户输入错误的学号或密码。
  1. 如果系统检测到学号或密码不匹配，系统提示用户“学号或密码错误”。
  2. 用户可以重新输入正确的学号和密码。
- **替代流 2**：用户忘记密码。
  1. 用户点击“忘记密码”链接。
  2. 系统要求用户通过邮件或短信验证身份。
  3. 用户重置密码后再次尝试登录。

### 后置条件
- 用户成功登录后，系统将用户的会话标记为活跃状态。
- 系统会保存用户的登录状态，直到用户主动退出登录。

## 用例 2: 发布帖子

### 用例描述
- **用例名称**：发布帖子
- **角色**：用户
- **目标**：用户能够在平台上发布帖子，分享信息或二手交易等。

### 前置条件
- 用户已经登录到系统。
- 用户已选择“发布帖子”功能。
- 用户准备好要发布的帖子内容。

### 基本流
1. 用户进入平台首页并点击“发布帖子”按钮。
2. 系统打开发布帖子页面，用户输入帖子的标题、内容和选择合适的标签。
3. 用户可以上传相关的图片或附件。
4. 用户点击“发布”按钮。
5. 系统验证帖子内容是否合法（如是否含有敏感词、非法内容等）。
6. 如果内容合法，系统保存帖子并将其发布到平台。
7. 发布的帖子出现在用户的主页以及平台的相关帖子列表中。

### 替代流
- **替代流 1**：帖子内容包含不符合平台规定的敏感词。
  1. 系统检测到敏感词后，提示用户“帖子内容包含不允许的词汇”。
  2. 用户修改帖子内容后重新发布。
- **替代流 2**：用户没有上传图片或附件。
  1. 用户可以选择发布仅含文字的帖子，不上传任何附件。

### 后置条件
- 发布的帖子会立即出现在平台的帖子列表中。
- 用户的帖子被标记为“已发布”状态，可以被其他用户查看、评论或互动。

## 用例 3: 管理员审核帖子

### 用例描述
- **用例名称**：管理员审核帖子
- **角色**：管理员
- **目标**：管理员能够审核用户发布的帖子，删除违规内容或标记为不合规。

### 前置条件
- 管理员已经登录到后台管理系统。
- 平台有需要审核的帖子（例如，用户举报或自动检测到不合规内容的帖子）。

### 基本流
1. 管理员进入后台管理界面，查看待审核的帖子列表。
2. 管理员点击待审核帖子查看帖子内容。
3. 管理员判断帖子是否符合平台规定（包括内容、语言、图片等）。
4. 如果帖子符合规定，管理员点击“批准”按钮，帖子状态更新为“已审核”并公开。
5. 如果帖子不符合规定，管理员点击“删除”按钮，帖子从平台移除。
6. 系统自动向用户发送邮件或通知，告知其帖子已被删除或已通过审核。

### 替代流
- **替代流 1**：管理员查看到帖子中存在违规内容。
  1. 管理员将帖子标记为“待处理”并通知相关用户进行修改。
  2. 用户修改帖子后重新提交审核。
- **替代流 2**：管理员忽略某些小问题帖子。
  1. 管理员决定保留帖子，仅提醒用户注意平台规定。

### 后置条件
- 如果帖子审核通过，它将公开在平台上供其他用户查看。
- 如果帖子被删除，相关内容将从平台上彻底移除，并通知用户。
- 平台将记录管理员的操作日志，以便后续审查。

# 3.3

## 1. 是否遗漏了异常流？

### 人工版本

- **用例：用户登录**
  - **异常流**：
    - 用户输入错误的学号或密码。
    - 用户忘记密码并需重置。
  - **分析**：在这个用例中，人工版本详细覆盖了两种常见的登录异常情况：输入错误和密码重置。这些异常是用户在使用登录功能时经常遇到的情况，因此非常重要。没有遗漏。

- **用例：发布帖子**
  - **异常流**：
    - 帖子内容包含不符合平台规定的敏感词。
    - 用户没有上传图片或附件。
  - **分析**：人工版本在发布帖子时考虑了常见的异常场景，如内容检测和附件缺失，都是用户在实际使用过程中可能遇到的情况。完整地覆盖了这些异常情况。

- **用例：管理员审核帖子**
  - **异常流**：
    - 管理员发现帖子中存在违规内容。
    - 管理员忽略某些轻微问题的帖子。
  - **分析**：人工版本对异常流的处理也相当全面，涉及到管理员在审核过程中的两种可能的情况：处理违规内容和忽略某些轻微问题。此部分异常流的补充对于保证平台运营的合规性非常重要。

**总结**：人工版本对异常流的描述非常充分，每个用例都覆盖了可能出现的不同异常情况，体现了全面的考虑。

### AI 版本

- **用例：发布任务**
  - **异常流**：
    - 输入为空 → 提示错误。
    - 网络异常 → 发布失败。
  - **分析**：AI 版本提供了两个常见的异常场景，异常处理较为基础，涵盖了输入错误和网络问题。在实际应用中，这些确实是常见问题，但可能忽视了例如任务标题重复、任务描述不清等细节问题。

- **用例：接单**
  - **异常流**：
    - 任务已经被其他接单者接走 → 提示失败。
  - **分析**：AI 版本考虑到了一个常见的异常流：任务已被接走。但在一些细节上，比如接单者的资格验证、任务状态不一致等问题，AI 版本的描述略显简化。

- **用例：完成任务**
  - **异常流**：
    - 发布者拒绝确认任务完成 → 进入申诉流程。
  - **分析**：这部分异常流考虑得相对充分，处理了任务完成确认过程中可能出现的纠纷，并提供了处理申诉的机制，符合实际操作需求。

**总结**：AI 版本涵盖了大多数常见的异常流，但在细节方面存在一定的简化。例如，接单时任务信息不一致、任务重复等边界异常并未考虑到。

## 2. 验收标准是否具体可测试？

### 人工版本

- **用例：用户登录**
  - **验收标准**：
    - 用户可以成功输入正确的学号和密码。
    - 系统应当正确验证学号和密码。
    - 成功登录后，系统应标记用户会话为活跃状态，并显示用户主页或个人信息。
  - **分析**：这些验收标准非常具体且可操作，能够通过手动或自动化测试来验证。例如，验证学号和密码的正确性是标准的登录测试，登录后的会话状态也可以通过系统行为来验证。

- **用例：发布帖子**
  - **验收标准**：
    - 用户能够发布包含标题、内容和标签的帖子。
    - 帖子不包含敏感词或其他非法内容。
    - 发布的帖子能够成功显示在平台上。
  - **分析**：验收标准非常清晰、可测试。可以通过手动验证或者自动化工具对帖子的内容合法性进行检查，确保内容符合平台规则。

- **用例：管理员审核帖子**
  - **验收标准**：
    - 管理员能够查看并审核待审核的帖子。
    - 管理员可以删除违规的帖子，并且会及时通知用户。
  - **分析**：人工版本的验收标准十分明确，涵盖了管理员操作的每一个环节，并且可通过系统测试来验证是否能够成功执行这些任务。

**总结**：人工版本中的验收标准非常具体，清晰地描述了期望的系统行为，并能通过标准的测试方法进行验证。

### AI 版本

- **用例：发布任务**
  - **验收标准**：
    - 用户可以输入任务标题、描述和价格，任务发布成功。
  - **分析**：验收标准简单明确，符合测试要求。但可以进一步细化，例如如何处理用户输入的非法字符、网络不稳定等异常场景，增加更多细节描述。

- **用例：接单**
  - **验收标准**：
    - 接单成功后，任务状态更新为已接单。
  - **分析**：这个验收标准能够验证接单功能是否正常，但还可以进一步明确接单后是否有任何通知发送，是否有状态检查等。

- **用例：完成任务**
  - **验收标准**：
    - 任务完成后，系统更新任务状态为已完成。
  - **分析**：这是一个简洁且可测试的标准，可以通过检查任务状态的变化来验证功能。但如果考虑到更多边界条件，如任务被错误拒绝或发生冲突时的处理，标准会更为完备。

**总结**：AI 版本的验收标准非常简洁，虽然具备可测试性，但可以在细节上加强，确保涵盖更复杂的场景和系统行为。

## 3. 总结对比

- **异常流覆盖**：人工版本对每个用例都进行了详细的异常流描述，覆盖了实际操作中可能遇到的各种问题，确保系统能够处理各种异常情况。相比之下，AI 版本虽然涵盖了一些常见的异常流，但没有详细考虑更多可能的边界情况或特殊情形，建议补充更多的异常场景。

- **验收标准**：人工版本的验收标准非常具体，清晰地描述了期望的系统行为，并能通过标准的测试方法进行验证。AI 版本虽然简洁明了，但在描述上略显基础，建议增加更多细节，特别是针对不同情境下的反馈和状态更新。

### 总体建议
- 对于 **AI 版本**，可以通过添加更多的异常流和更详细的验收标准，使其在实际应用中更加全面和可操作。
- 对于 **人工版本**，已经很好地覆盖了所有细节，唯一需要注意的就是确保每次迭代都能加入新的使用场景和异常流，保持系统的灵活性和鲁棒性。
